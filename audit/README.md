# Data audit records

One record per run, so every published number can be checked after the trajectory
data behind it is gone. The benchmark produced 35.7 GB of trajectories; the records
that replace them are 3 MB.

| record | run | engine | trajectories excluded |
|---|---|---|---|
| `spc_gromos/` | SPC production | GROMOS, Gadi | 11.2 GB |
| `spce_gromos/` | SPC/E production | GROMOS, Gadi | 11.2 GB |
| `spc_gromacs/` | SPC production | GROMACS, Setonix | 2.2 GB |
| `spce_gromacs/` | SPC/E production | GROMACS, Setonix | 2.2 GB |
| `opc3_gromacs/` | OPC3 production | GROMACS, Setonix | 2.2 GB |
| `opc3_settings/` | OPC3 1.4 nm / 2 fs sweep | GROMACS, Setonix | 3.3 GB |
| `diagnostics/` | protocol variations | GROMACS, Setonix | 3.3 GB |

## What each record holds

    inputs/       every .imd / .mdp, the topology, the starting configuration (gzipped)
    logs/         the engine's own log, trimmed; scheduler output
    provenance/   SHA256SUMS.txt over audited *and* excluded files; per-job records
    results/      the analysed numbers this run contributed

`spc_gromos/` was assembled by hand first and carries more: a written provenance
narrative and per-replicate analysis. The rest are generated by
[`water_benchmarking.audit`](../src/water_benchmarking/audit.py) (`build()`), which
generalises it.

## What is auditable, and what is not

**Energies are kept; trajectories are not.** This is the one asymmetry to understand
before relying on a record:

| property | recomputable from what remains? |
|---|---|
| Density | **yes** — the `.edr` / `.tre.gz` stay beside the run |
| ΔH_vap | **yes** — same |
| Self-diffusion D | no — needs coordinates |
| τ₂(HH), τ₁(μ) | no — needs coordinates |
| Dielectric constant ε | no — needs coordinates |

The energy files are a few MB and were kept for exactly this reason; the
trajectories are ~1 GB per nanosecond and were not. For the three properties that
cannot be recomputed, the record carries the computed value, the inputs that
produced it, the engine's own log of the run, and a SHA-256 of the trajectory it
came from — so a restored copy can be *proved* to be the same data
(`sha256sum -c`), even though it cannot be regenerated from here.

Re-running is the other route: every record carries a complete input set, and the
runs are reproducible from them (`water-bench build`, then `submit-gromacs` or
`run`). The seeds are in the `.mdp` / `.imd` files, so a re-run reproduces the same
trajectory, not merely an equivalent one.
